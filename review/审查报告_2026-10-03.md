# CoreCoder 项目审查报告

审查日期：2026-10-03。对象：本地 fork `im-xiaochen/CoreCoder`，版本 **0.7.0**，`main` 分支，提交 **c2d841719019a96346c42173ed96dbe71c5cdeda**。

## 1. 结论

CoreCoder 的核心闭环完整，适合作为理解编程 agent、开发个人定制版本的起点。它已经具备流式模型调用、八个内置工具、工具授权、计划模式、hooks、MCP stdio、子 agent、上下文压缩和会话保存。源码职责清楚，现有测试对许多异常路径也有覆盖。

如果目标是让这个 fork 成为日常使用的编程助手，最值得先投入的是**状态隔离、路径一致性和修改可恢复性**。这些直接决定“是否在正确的目录、使用正确的授权、可靠地修改文件”。随后再补长任务预算、会话恢复和代码检索能力。

本次运行原有 **214 个测试，全部通过**；`ruff check corecoder tests` 通过。在此基础上，额外复现了 **11 项问题、13 个触发场景**。测试全绿说明已有用例覆盖的行为正常，并不表示以下场景已被覆盖。

本次只新增审查材料和离线复现脚本，没有修改运行源码、提交 commit 或推送到 GitHub。

## 2. 项目结构和现状

| 层次 | 主要文件 | 已有能力 | 当前主要限制 |
|---|---|---|---|
| 调度 | `agent.py` | 模型—工具循环、批量并行、工具异常转结果、中断消息回填 | 状态分散、并行不判断依赖、缺少结构化完成状态 |
| 模型 | `llm.py`、`config.py` | OpenAI 兼容流、LiteLLM 可选后端、重试、token 与费用估算 | 无统一预算；切换模型后费用计算错误 |
| 上下文 | `context.py`、`prompt.py` | 截短、摘要、应急压缩、任务清单注入 | 无硬预算保证，摘要遗漏工具参数 |
| 工具 | `tools/` | 读写、精确替换、shell、搜索、任务清单、子 agent | shell 与文件工具使用不同工作目录来源 |
| 授权和扩展 | `permissions.py`、`hooks.py`、`mcp.py` | 单次或持久授权、调用前后 hooks、外部工具 | 授权粒度粗，MCP 只取工具列表第一页 |
| 交互和恢复 | `cli.py`、`session.py`、`checkpoints.py` | REPL、斜杠命令、存档、恢复、撤销 | 恢复信息不完整，撤销缺少冲突检查 |

值得保留的设计包括：精确唯一匹配编辑、写文件工具之间的锁、工具拒绝理由进入模型上下文、子 agent 不携带继续派生工具，以及中断后补齐 tool reply。它们为后续完善提供了清楚的落点。

README 明确将项目定位为最小教学实现，并承认 shell 黑名单、无硬预算、无 RAG、MCP 仅实现工具等取舍。因此本报告将实际缺陷和新增功能建议分开，不把所有未实现能力都当作 bug。

## 3. 已复现问题及优先级

P1：优先修复，涉及授权归属、错误文件操作、数据覆盖或长任务无法继续。P2：随后修复，涉及失败恢复、统计、脚本集成或扩展兼容性。以下均针对审查提交，而非对其他版本的推断。

### R01：多 agent 默认状态串用

**位置：** [agent.py:36](E:/github项目/CoreCoder/corecoder/agent.py:36)、[agent.py:49](E:/github项目/CoreCoder/corecoder/agent.py:49)、[tools/__init__.py:12](E:/github项目/CoreCoder/corecoder/tools/__init__.py:12)、[tools/agent.py:45](E:/github项目/CoreCoder/corecoder/tools/agent.py:45)。

`ALL_TOOLS` 保存已经创建好的对象。每个默认 `Agent` 都引用这批对象，并将共享 `AgentTool._parent_agent` 改为自己；后创建的 B 因而覆盖 A 的父对象。默认 Todo 工具也共享。

**复现结果：** A 只批准派生子任务、拒绝写文件，B 为自动批准模式；A 调用子任务时，实际使用了 B 的模型和授权，成功写入测试文件，A 的写入授权回调没有收到请求。B 的系统上下文同时能看到 A 的任务清单。

**影响范围：** 主要是同一 Python 进程内嵌入多个默认顶层 agent 的场景。通常只建立一个顶层 agent 的 CLI 使用方式不会单独触发这个跨实例问题。

**建议：** 默认工具改为工厂，每个顶层 agent 拿到新实例；把工作目录、Todo、授权、修改记录明确放进会话状态对象。子 agent 显式共享需要共享的授权和模型，单独维护任务状态。仅复制 `ALL_TOOLS` 列表不能解决对象共享。

**验收：** A、B 的 Todo、父指针、工作目录互不干扰；A 的子任务始终使用 A 的授权；为两种不同授权模式加入交叉用例。

### R02：工作目录存在两套语义

**位置：** [tools/bash.py:84](E:/github项目/CoreCoder/corecoder/tools/bash.py:84)、[tools/read.py:36](E:/github项目/CoreCoder/corecoder/tools/read.py:36)、[tools/write.py:37](E:/github项目/CoreCoder/corecoder/tools/write.py:37)。编辑、glob、grep 也通过 `Path(...).resolve()` 解析相对路径。

shell 使用线程局部 `tracked_cwd`，文件工具使用 Python 进程的实际 cwd。shell 执行 `cd sub` 不会改变后者。

**复现结果：** 根目录和 `sub` 各放一个同名 `marker.txt`，内容分别为 ROOT、SUB。`bash("cd sub")` 成功，随后 `read_file("marker.txt")` 读到 ROOT。写文件工具同样存在落到错误同名路径的可能。

**建议：** 用统一会话工作目录解析所有工具路径，并在工具结果和系统上下文中显示当前目录。不要在多 agent 进程内用全局 `os.chdir()` 修补，否则会引入新的共享状态问题。

**验收：** cd 后 read/write/edit/glob/grep 一致；子 agent 起始目录正确且不会反向改变父目录；覆盖含空格、中文的 Windows 路径。

### R03：`/undo` 缺少外部修改冲突检查

**位置：** [checkpoints.py:51](E:/github项目/CoreCoder/corecoder/checkpoints.py:51)、[checkpoints.py:63](E:/github项目/CoreCoder/corecoder/checkpoints.py:63)、[checkpoints.py:73](E:/github项目/CoreCoder/corecoder/checkpoints.py:73)。

快照只有修改前的内容。撤销时不验证当前文件是不是 agent 修改后的版本，直接恢复旧内容；新建文件的撤销则直接删除。

**复现结果：** original → agent change → later human change → undo，最终为 original，人工追加的修改被覆盖。

**建议：** 保存修改前内容以及修改后 hash；撤销前比较当前 hash，冲突时保留当前文件并显示差异，提供显式强制撤销选项。记录按工作区和会话划分。当前全局 `~/.corecoder/checkpoints.json` 的跨会话历史是已有设计，但跨项目撤销目标不够透明。

**验收：** 无外部修改可直接撤销；有外部修改时拒绝覆盖并保留快照；新建文件后来被修改时，不直接删除；先显示待撤销文件路径。

### R04：撤销操作不是事务

**位置：** [checkpoints.py:63](E:/github项目/CoreCoder/corecoder/checkpoints.py:63)、[cli.py:280](E:/github项目/CoreCoder/corecoder/cli.py:280)。

代码先 `_stack.pop()`，再恢复文件。恢复失败时条目已经从内存删除；REPL 的 `/undo` 分支也位于包围 `agent.chat()` 的异常捕获之外。

**复现结果：** 模拟恢复写入失败，`undo()` 抛出 `OSError`，随后 `pending()` 为 0。磁盘上的旧快照此时可能仍在，重启可能重载它，所以并非所有失败都永久丢失历史；但当前进程状态已经不一致。

**建议：** 先读取栈顶并完成恢复，成功后才删除条目和持久化；统一处理斜杠命令错误，使 REPL 保持可用。恢复和普通编辑使用同一文件锁。

**验收：** 权限不足、磁盘写入失败等情况下，条目仍可重试，REPL 不退出。

### R05：压缩没有保证满足上下文预算

**位置：** [context.py:67](E:/github项目/CoreCoder/corecoder/context.py:67)、[context.py:93](E:/github项目/CoreCoder/corecoder/context.py:93)、[context.py:106](E:/github项目/CoreCoder/corecoder/context.py:106)、[context.py:142](E:/github项目/CoreCoder/corecoder/context.py:142)。

`_safe_split()` 为保持 tool-call/reply 完整，会将切点回退到整组开始。如果最近一组很大，切点可能退到 0，压缩保留全部内容，又增加两条摘要消息。单行或少于七行的长工具输出也不会被第一层截短。

**复现结果：** 用 100 token 的受控小窗口、6 个同组工具结果验证：估算 token 从 **2001 增为 2029**，却返回 `compressed=True`。小窗口只是方便复现，相同控制流程也适用于较大的实际窗口。

此外，当前预算只估算历史消息，没有计入系统提示、工具 schemas 和预留的模型输出空间；切换模型也不自动更新窗口配置。

**建议：** 将“执行了压缩”和“请求已满足预算”分开；对保留组内的超大结果按字符/token 截短，原文存到可分页读取的文件；计入完整请求和输出预留。预算无法满足时给出明确终止原因，避免继续发送必然超限的请求。

**验收：** 单个超大结果、超大同组调用、很多 MCP schemas、长中文输入均能压到预算内，或明确拒绝继续。

### R06：摘要遗漏执行参数和较后信息

**位置：** [context.py:161](E:/github项目/CoreCoder/corecoder/context.py:161)、[context.py:177](E:/github项目/CoreCoder/corecoder/context.py:177)、[context.py:189](E:/github项目/CoreCoder/corecoder/context.py:189)。

`_flatten()` 只提取每条消息前 400 字的 `content`，不包含 `tool_calls`；总摘要输入又只取前 15000 字。工具名、参数、替换内容等若只在调用中出现，就不会进入摘要。即使摘要模型可靠，也无法恢复没收到的信息。

**复现结果：** 一个没有正文、仅带 edit 参数的 assistant 消息，参数中唯一的修改决定完全不在摘要输入里。

**建议：** 为摘要提供结构化执行记录，保留修改文件、关键参数摘要、成功/失败、测试结论、用户约束和未完成工作。长历史采用分块摘要与增量记忆，避免固定保留最早一段。

**验收：** 压缩后还能指出具体改动、用户约束及剩余任务；检查关键事实保留情况，而不只检查 token 是否变少。

### R07：异常工具参数可能破坏后续会话

**位置：** [llm.py:247](E:/github项目/CoreCoder/corecoder/llm.py:247)、[agent.py:97](E:/github项目/CoreCoder/corecoder/agent.py:97)、[agent.py:115](E:/github项目/CoreCoder/corecoder/agent.py:115)、[cli.py:356](E:/github项目/CoreCoder/corecoder/cli.py:356)。

流式参数 `json.loads()` 的结果不保证是对象；JSON 解析失败则静默替换为 `{}`。格式化回调、hooks、授权都发生在执行参数绑定之前，且待执行调用只在 `KeyboardInterrupt` 时补齐消息。

**复现结果：** 参数为合法 JSON `[]`，进入授权提示的 `_brief()` 后触发 `AttributeError`，历史留下 assistant tool call，却没有对应 tool reply。真实 CLI 的工具显示回调也会在相同形状下失败。后续请求因消息链不完整而存在被兼容接口拒绝的风险。

**建议：** 在任何回调或 hook 之前验证参数是对象并符合工具 schema；将格式错误变成明确的工具错误结果。确保所有调用最终都有对应 reply，含回调、hook、授权异常；不要在无法判断执行结果时报告为已成功。

**验收：** 对 `[]`、`null`、字符串、截断 JSON、错误参数类型、未知工具的输入，agent 保持可继续对话且消息链完整。

### R08：费用账本随当前模型变化

**位置：** [llm.py:119](E:/github项目/CoreCoder/corecoder/llm.py:119)、[cli.py:250](E:/github项目/CoreCoder/corecoder/cli.py:250)。

所有请求用量累加到两个计数器，`estimated_cost` 则只使用当前模型的单价，因此模型切换后，旧请求也被按新单价计费。

**复现结果：** 固定历史输入 100 万 token，在代码内置价格表下，由 `gpt-4o` 切换为 `gpt-4o-mini`，显示费用从 **$2.50 变为 $0.15**，期间没有新增请求。这里验证的是仓库计算逻辑，不代表核实了这些模型的现行报价。

**建议：** 按每次请求记录模型、用量和当时费率，再求累计值；为未知价格明确标记未知部分。若未来增加硬预算，应先完成账本修复，避免预算基于错误数值。

**验收：** 切换模型不改变过去费用；显示已知小计和未知用量；预留缓存、重试用量等字段。

### R09：one-shot 无法表达任务未完成

**位置：** [agent.py:124](E:/github项目/CoreCoder/corecoder/agent.py:124)、[cli.py:155](E:/github项目/CoreCoder/corecoder/cli.py:155)。

达到 `max_rounds` 时，`Agent.chat()` 返回字符串；`_run_once()` 只依赖流式回调输出，忽略返回值，并正常返回。因此调用脚本可能得到成功退出码，却未获知 agent 耗尽轮次。

**复现结果：** 受控设为一轮且仍有工具调用，`_run_once()` 正常返回，输出不包含达到上限原因。

**建议：** 返回结构化结果：`completed / max_rounds / cancelled / failed`、文本、工具错误、用量等；CLI 映射明确退出码；增加 `--json`，把诊断移到 stderr。模型结束回答也不等于业务任务一定成功，结构化结果应保留工具失败信息。

**验收：** 正常完成、轮次耗尽、异常、中断各有稳定机器可读状态；CI 可识别未完成任务。

### R10：配置容错只处理语法，不处理结构

**位置：** [hooks.py:65](E:/github项目/CoreCoder/corecoder/hooks.py:65)、[mcp.py:194](E:/github项目/CoreCoder/corecoder/mcp.py:194)、[session.py:67](E:/github项目/CoreCoder/corecoder/session.py:67)。

**复现结果：** `{"PreToolUse":[42]}` 和 `{"mcpServers":[42]}` 分别使加载器抛 `AttributeError`；会话存档为 `[]` 时抛 `TypeError`，而不是按“坏存档返回 None”的接口处理。

**建议：** 校验根类型、字段类型、消息 roles 和必填字段；错误指明文件与字段，并跳过无效配置项。会话保存用临时文件加原子替换，避免直接写入造成截断；加入存档格式版本，为后续迁移留入口。

**验收：** 无效嵌套结构、字段缺失、部分服务器配置错误、截断存档都不会意外终止正常 CLI；有效项仍可加载。

### R11：MCP 工具分页不完整

**位置：** [mcp.py:71](E:/github项目/CoreCoder/corecoder/mcp.py:71)。

工具发现只调用一次 `tools/list`，随后直接注册 `tools` 数组。所使用的 MCP 2025-06-18 规范支持 `cursor` / `nextCursor` 分页。[规范来源](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

**复现结果：** 离线假服务端第一页返回 first 和 `nextCursor=page2`，第二页提供 second；客户端只注册 first。

**建议：** 拉取所有页，防止重复 cursor 无限循环；验证握手结果并显示协商版本。后续再加入工具列表变更通知、结构化结果处理和明确的客户端生命周期。

**验收：** 多页发现、重复 cursor、服务器在分页中途退出均有确定结果，工具名冲突可检测。

## 4. 值得完善的功能

| 可取消的工具执行 | Ctrl+C 后及时停止副作用 | 取消未开始任务、终止进程树、清楚报告已完成/未执行/结果未知 | 大 |
| 大仓搜索和分页读文件 | 找代码更快、上下文更稳定 | 优先复用 rg、尊重 `.gitignore`、排除二进制、限制单文件大小、分页返回结果 | 小至中 |
| 项目说明自动加载 | 定制行为符合仓库规范 | 分层读取 AGENTS.md 或 CORECODER.md，明确优先级；限制长度并区别指令与检索内容 | 小至中 |
| 结构化执行记录 | 更容易定位为什么失败 | 记录调用 ID、目标路径、结果、耗时、预算和完成状态；敏感字段可脱敏 | 中 |
| 启动诊断 | 降低首次配置成本 | `/doctor` 检查配置结构、依赖、Git Bash、模型端点和 MCP 进程；网络探测显式执行 | 小 |

### 需要在实现时处理的几处工程约束

**并行执行应先识别冲突。** 当前一个 batch 中所有获准调用直接进线程池；写文件工具的锁避免读改写交错，却不能让“写文件→跑测试”或“cd→下一条命令”按依赖执行。建议首版只并行明确只读的独立调用，变更调用按顺序执行；后续增加每个工具的副作用和资源声明。并发子 agent 若需要交互授权，也应统一回到主线程请求输入。

**终止模型循环不等于终止外部进程。** `ThreadPoolExecutor` 退出时会等待正在运行的任务；shell 和 hooks 没有显式进程树管理，MCP 调用超时也没有协议取消。要实现可靠取消，需要进程组或 Windows Job Object，以及结果未知状态，不能只补一个 try/except。[Python 线程池文档](https://docs.python.org/3/library/concurrent.futures.html#concurrent.futures.Executor.shutdown)

**输出限制应发生在采集阶段。** shell 用 `capture_output=True` 收集完整输出后才截短，read/grep 先读取完整文件，glob 先收集全部命中再截短。因此显示长度有上限，内存和遍历成本仍无对应硬上限。适合先用流式读取、分页和扫描上限完善，暂不必搭建向量数据库。[Python subprocess 文档](https://docs.python.org/3.10/library/subprocess.html#subprocess.Popen.communicate)

**安全能力应按实际目标分层。** 现有 shell 正则是防手滑的黑名单，README 也明确它不是沙箱；文件读写没有工作区路径边界。个人可信项目可先增加可见、可撤销的工作区授权。若未来运行不可信仓库或自动化任务，再提供容器或系统隔离，不能把正则命中与否当成安全保证。hooks 是用户配置的 shell 命令，pre-hook 在计划模式和工具授权前执行；“计划模式只读”目前约束的是工具调用，不保证整个进程不产生副作用。

## 5. 建议实施顺序

### 第一阶段：先保证修改正确、可恢复

1. R01、R02：工具实例工厂和会话工作目录统一，明确父子 agent 状态归属。
2. R03、R04：撤销增加冲突检查，失败不丢条目，错误不退出 REPL。
3. R07、R10：参数与配置结构校验，异常后保证工具消息完整。

这一阶段的交付标准是：不会因状态串用使用其他会话的授权；不会因相对目录混淆改错文件；不会静默覆盖用户后续修改。

### 第二阶段：让长任务和脚本运行可靠

1. R05、R06：请求级上下文预算、可分页大输出、结构化摘要。
2. R08、R09：请求级费用账本、明确结束原因和 CLI 退出码。
3. 补充完整会话恢复、权限管理、真正的 diff 和结构化执行记录。

### 第三阶段：提高大仓效率和扩展性

1. R11：MCP 分页和客户端生命周期。
2. rg 检索、项目说明、冲突感知调度与取消。
3. 在上述能力稳定后，按实际使用数据决定是否添加语义索引、异步子 agent、模型 fallback 或图形界面。

优先选择能让具体任务完成得更稳的增强；仅增加一个 UI 或更多 provider，并不能解决文件目标错误和撤销冲突。
