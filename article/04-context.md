# 用有限的窗口，扛住一个长任务

agent 有一个绕不过去的物理约束：上下文窗口就那么大。

而编码任务偏偏极其能产 token。模型读一个一千行的文件，那一千行连同行号全进了历史；跑一次测试，几百行输出全进了历史；grep 一下，几十个匹配全进了历史。一个稍微像样的任务转上十几轮，几万 token 就没了。窗口一旦塞满，要么 API 报错，要么你得砍历史，而砍历史砍不好，agent 就会「忘事」，前面读过的文件转头又读一遍，刚做过的决定又推翻重来。

所以怎么在有限窗口里装下一个长任务，是 agent 工程里最硬核的子问题之一。这一篇看 `corecoder/context.py`（587 行）怎么解。

## 分层，从轻到重

打开 [`ContextManager.prepare_request()`](../corecoder/context.py)。每轮模型请求前，`Agent._run_turn()` 先把当前系统提示、工具 schema 和历史交给它。预算还包含安全余量和为输出预留的 token。准备好的请求已经放得下，就可以直接发出。

估算器可以使用 tokenizer，否则会根据中文字符、其他文字和符号密度做近似估算。估算对象也有讲究。`LLM.project_messages()` 会先过滤只属于其他模型或端点的推理字段，再计算请求体积。换模型恢复会话时，历史仍保留那段推理，但发送请求和估算窗口时都会跳过它。

下面从 `Agent._run_turn()` 摘出关键几行，省略产物目录等参数。

```python
prepared = self.context.prepare_request(
    self.messages,
    system=system,
    tools=self._tool_schemas(),
    output_reserve=output_reserve_for(self.llm, 4096),
    llm=self.llm,
)
if not prepared.budget_ok:
    raise ContextBudgetExceeded(prepared.reason or "context_budget_exceeded")
```

## 第一层：旧的工具输出，是有保质期的

窗口快满时，先找特别长的工具结果。压缩器把全文写入会话的产物目录，给模型留一段预览、可回读的路径、SHA-256 和字符范围。这份引用回答了两个问题：结论从哪儿来，以及要重新核对时去哪里读全文。

假设 grep 返回了几百行匹配，模型已经看过了。下一轮大多只需要知道搜过哪些地方，把全文留在磁盘上就能省下窗口。归档失败时，准备请求会返回明确的失败并保留原历史。

## 第二层：让模型给旧对话写个摘要

只缩工具结果还不够时，`prepare_request()` 在工具回合边界切出旧历史，先保存原始消息，再生成带归档引用的证据摘要。摘要需要区分工具成功、失败、拒绝和中断。模型曾经说要跑测试，与测试确实执行且通过，是两件事。

摘要调用也消耗 [本次运行的预算](03-llm-and-cost.md)。压缩后的版本确实比当前版本省 token，才会替换请求中的旧消息。最近的对话仍留给模型继续完成当前任务。

## 那个一定会咬你的坑：孤儿 tool 消息

一条带 `tool_calls` 的 assistant 消息和对应的 tool 回复要成组保留。切分点落在其中一个结果上时，只留下半组，下一次请求就可能被供应商拒绝。`_safe_split()` 会把切分点向前移，避开带工具调用的消息和工具回复。看 [主循环](01-the-loop.md) 时记下的 `tool_call_id` 配对，在这里同样适用。

## 第三层：最后手段

如果摘要之后仍超出窗口，系统会进一步缩短已经有全文备份的工具预览。固定部分或最新用户输入就已经过大，或者所有可缩内容处理后仍放不下，运行失败并给出 `context_budget_exceeded` 诊断并保留原始历史。用户可以缩小任务范围，或改用有更大窗口的模型。

## 和 Claude Code 的对照

旧版 CoreCoder 曾按窗口比例触发截断、摘要和硬折叠。当前实现把判断收拢到请求准备阶段。压缩策略的优先级仍然由便宜到昂贵，但是否继续压缩，取决于下一次请求究竟还差多少空间。

## 这一篇带走什么

- 每轮发出前都检查输入和输出预留，估算按实际会发送的消息做。
- 先归档全文再缩预览或摘要，模型可以凭路径和哈希回查。
- 切分时保全工具调用和回复的配对，放不下时保留原历史并明确报错。
