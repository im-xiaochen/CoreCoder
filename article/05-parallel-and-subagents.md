# 并行执行与子 agent

第一篇讲主循环时，我在「执行工具」那一步留了个口子：模型一次只要一个工具，和一次要好几个工具，走的是两条不同的路。这一篇先把这个口子补上，再讲一个让 agent 能给自己「分身」的工具。两件事其实是同一个主题的两面：怎么让一个 agent 同时处理多件事，而不互相搞乱。

## 一次回来好几个工具调用

模型一次可以返回多个工具调用。CoreCoder 只在整批调用都是 `read_file`、`glob`、`grep` 或 `repo_map` 时用线程池，最多 8 个 worker。线程可以按各自的速度完成，回给模型的结果仍按原来的调用顺序排列。

混合批次按顺序执行。比如同一批先写文件再读文件，顺序执行能让读操作看到这次写入的结果。源码入口是 [`Agent._exec_tools_parallel()`](../corecoder/agent.py)。

## 这个简化，相对 Claude Code 差在哪

这里的并发始于一批完整的工具调用。主循环等模型把这轮输出收完，再决定如何安排执行。工具读取并发、混合批次串行，给这段小循环留了一个容易核对的顺序。

## 并行不是免费的：共享可变状态会咬人

工作目录跟着会话走。绑定到会话的工具从 [`SessionState`](../corecoder/state.py) 解析相对路径，子代理用 `parent.state.fork()` 得到自己的目录和待办状态。一开始它在父会话的目录，之后改变子会话的目录，父会话仍停在原处。

隔离会话状态不等于给每个子代理各发一份额度。成员各自记录用量，物理请求统一从父运行已配置的预算扣减，父运行可以汇总整个团队的用量。

## 子 agent：给自己开一个分身

`agent` 工具有两种调用形态，`task` 和 `tasks` 二选一。单任务形态启动一个子代理并同步返回，仍走既有的父级权限流程。工具按子会话重新绑定，子代理走 `chat_result()`，因此失败和轮次耗尽都有各自的终态。Ctrl+C 会传回父代理，停止父运行。

团队形态给任务起名，再用 `depends_on` 表示先后关系。比如先分别读工具注册和预算代码，再汇总两份发现。下面是传给 `agent` 工具的参数：

```json
{
  "tasks": [
    {"name": "registry", "task": "阅读 corecoder/tools/__init__.py，列出工具注册入口"},
    {"name": "budget", "task": "阅读 corecoder/budget.py，说明请求额度何时预留"},
    {"name": "summary", "task": "汇总前两项结论和对应证据", "depends_on": ["registry", "budget"]}
  ]
}
```

[调度器](../corecoder/team.py) 接受 1 至 8 项任务，最多 4 项同时执行。启动前会检查重复名称、未知依赖和循环依赖。前置任务成功后，后续任务才会收到其摘要和证据引用。某项失败时，依赖它的分支会跳过，无关分支可以继续。预算耗尽或父级取消会停止新调度和后续发送，已经发出的请求仍需结算。每个成员的摘要有长度限制，写入成功时，全文保存在会话产物里。写入错误会单独报告。

## 为什么子 agent 不准生孙 agent

单任务工具集里没有 `agent`，团队成员也拿不到它。团队成员只继承受信任的内建只读工具和自己的待办工具，不能使用 shell、修改工作区的工具或 MCP。父级仍经过原有授权与钩子流程，成员不加载钩子。这样你可以把调查拆给几个人，而所有改动仍留给父运行处理。

## 和 Claude Code 的对照

CoreCoder 提供的是一次父运行里的只读调查。团队按显式依赖调度，结果在本次运行里收齐。Web 界面还会记录成员状态，断线后可以恢复显示，详见 [第六篇](06-session-and-cli.md)。

## 这一篇带走什么

- 同一轮的纯读取工具批次可以并行，混合批次按顺序执行。
- 子代理各自持有会话状态，团队共用父级已配置的运行预算。
- `depends_on` 控制启动顺序，结构化结果保留状态、用量与证据。
